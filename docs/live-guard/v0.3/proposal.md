최초 조치는 자체 정책과 서버 검증을 거쳐 자동 실행한다. 운영자는 이의제기와 근거 부족·실행 실패 등 예외를 검토한다. 임시 가림은 Backend 초기 규칙으로 수행하며, Agent의 판단을 근거로 하는 확정 조치도 운영자 사전 승인을 기다리지 않는다.

본 문서의 수치와 계약은 개발 시작 시 동결할 기본안이다. 시장 효과와 성능은 검증할 가설이며 구현 완료·평가 점수 획득을 뜻하지 않는다.

## 1. 프로젝트 배경 및 문제 정의

라이브 채팅은 운영자가 메시지를 읽고 판단하는 동안에도 계속 유입된다. 욕설, 반복 괴롭힘, 도배, 사칭·로그인 유도 메시지에 매번 사전 승인을 요구하면 처리 지연과 검토 부담이 발생할 수 있다.

단어 일치만으로는 정상적인 반응과 공격을 구분하기 어렵다.

| 메시지 | 맥락 | 검토 방향 |
| --- | --- | --- |
| “오늘 무대 진짜 미쳤다ㅋㅋ” | 공연에 대한 긍정적 반응 | 정상 |
| “너는 왜 맨날 그러냐. 방송 접어라.” | 같은 대상을 향한 반복 발언 | 괴롭힘 여부 조사 |
| “방송 접으라는 말은 하지 마세요.” | 공격 표현을 인용하며 제지 | 정상 예외 확인 |

해결하려는 문제는 유해 후보의 초기 노출, 단순 필터의 오탐, 맥락·이력·정책을 수동 조회하는 부담, 조치 근거와 실행 결과 추적의 어려움이다. **정책으로 범위를 정한 자동 조치와 사후 정정 절차를 함께 구현**한다.

### 1.1 고객과 사업 모델

| 항목 | 설계 가설 |
| --- | --- |
| 도입 고객 | 전담 Trust & Safety 조직이 없는 중소·중견 라이브·팬 플랫폼 운영사 |
| 현재 대안 | 금칙어 필터와 소수 운영자의 수동 검토 |
| 도입 형태 | 고객사 채팅 수신 API와 조치 반영 API를 어댑터로 연결 |
| 과금 | 채널 수 기준 월 구독 + 월 분석 사건 수 초과분 종량 과금 |
| 과금 집계 단위 | 최초 분석이 완료된 고유 case_id; 재시도·재조사·이의제기는 중복 과금하지 않는 가설 |
| 검증 항목 | 사건당 검토 시간, 자동 조치 오탐률, 분석 비용, 실제 지불 의향 |

실제 고객 연동과 결제는 MVP 범위에서 제외한다. 대형 플랫폼 대비 우위를 전제하지 않고, 전담 인력이 부족한 고객의 업무 부담 감소를 검증한다.

## 2. 서비스 목표 및 차별성

1. 위험 후보를 빠르게 선별하고 초기 가림 조건에 해당하는 메시지의 노출을 줄인다.
2. Agent가 필요한 맥락·이력·역할·공식 안내 정보를 선택 조회한다.
3. 자체 운영정책을 RAG로 검색해 판단 근거를 확보한다.
4. 서버가 허용 여부를 검증한 조치를 운영자 사전 승인 없이 실행한다.
5. 실행 결과를 확인해 운영자에게 보고하고 작성자에게 사유·기간·이의제기 방법을 안내한다.
6. 이의제기와 예외 상황은 운영자가 검토하고, 잘못된 조치는 취소·복구한다.

| 구분 | 단순 금칙어 필터 | LIVE:GUARD |
| --- | --- | --- |
| 판단 | 단어·패턴 일치 | 맥락·대상·반복 이력·정책 근거 |
| 처리 | 고정 규칙 차단 | 허용 범위 안의 자동 조치 |
| 근거 | 탐지 규칙 | 근거 메시지와 정책 조항·버전 |
| 운영자 역할 | 수동 확인·예외 처리 | 결과 확인, 이의제기와 예외 재검토 |
| 추적 | 탐지·차단 로그 | 판단·실행·보고·이의제기·복구 이력 |

비교 대상은 단순 금칙어 시스템이다. 실제 모든 플랫폼이 이 방식만 사용한다고 가정하지 않는다. **선조치란 운영자 승인보다 먼저 실행한다는 의미이며, 정책·권한 검증을 생략한다는 의미는 아니다.**

## 3. 주요 사용자 및 서비스 범위

MVP는 **LIVE:GUARD 관제 서비스**와 이를 시연하는 **가상 고객사 채팅 플랫폼**으로 구성한다. 시청자는 고객사 플랫폼 사용자이며, 그 플랫폼의 화면에서 본인 조치·이의제기를 이용한다. LIVE:GUARD의 직접 업무 사용자는 운영자·관리자다.

Spring Boot의 `platform` 모듈은 채팅·시청자 기능, `guard` 모듈은 필터·사건·조치·재검토를 담당한다. `ChatIngestPort`와 `ModerationActionPort` 인터페이스로 연결하고 실제 고객 연동 시 어댑터를 교체한다.

### 3.1 사용자

| 사용자 | 역할 |
| --- | --- |
| 플랫폼 운영사 | 관제 기능 도입, 자체 정책·권한 관리 |
| 시청자 | 채팅·신고, 본인 조치 확인·이의제기 |
| 담당 운영자 | 후보고 확인, 이의제기·예외 재검토, 취소·복구 결정 |
| 플랫폼 관리자 | 역할·채널 접근 권한과 운영 설정 관리 |

### 3.2 MVP 범위

| 항목 | 구현 내용 |
| --- | --- |
| 채널 | 시연용 채팅방 1개, 접근 제어 검증용 별도 채널 1개 |
| 위험 유형 | 반복 괴롭힘, 도배, 사칭·피싱 의심 외부 유도 |
| 초기 조치 | 규칙에 해당하는 메시지만 임시 가림 |
| 후속 자동 조치 | 정책 근거 확인 후 메시지 숨김 또는 한시적 채팅 제한 |
| 정정 | 정상으로 확인된 임시 가림 해제, 이의제기 후 운영자 결정에 따른 복구 |
| 이의제기 | 본인 조치 1건에 대한 사유 제출·검토 상태·결과 확인 |
| 기록 | 사건·정책·조치·보고·이의제기·실행 작업 상태 |
| 대기열 | RabbitMQ 조사·재개·재시도 작업 처리 |

계정 영구 정지, 실제 플랫폼 연동, 영상·음성 분석, 외부 사이트 접속을 통한 악성 여부 분석, 여러 Agent 협업은 제외한다. 한시적 채팅 제한은 해당 채널에만 적용하며 다른 채널 이용까지 제한하지 않는다.

### 3.3 메시지 공개 범위

| 상태 | 작성자 | 다른 시청자 | 담당 운영자 |
| --- | --- | --- | --- |
| `PUBLIC` 공개 | 표시 | 표시 | 표시 |
| `HELD` 임시 가림 | 표시·검토 상태 안내 | 미전달·이력 조회 제외 | 원문·가림 사유 |
| `HIDDEN` 정책에 따른 숨김 | 표시·조치 사유 안내 | 미전달·이력 조회 제외 | 원문·정책·실행 결과 |

원문은 보존하고 공개 상태를 따로 관리한다. SSE, 이력 API, 재접속 응답에서 같은 공개 범위를 적용한다. 이미 전달된 메시지는 후속 이벤트로 화면에서 숨길 수 있지만 전달된 원문 자체를 회수했다고 주장하지 않는다.

채팅 제한 상태는 메시지 상태와 별도다. 제한 중에는 서버가 새 메시지 전송을 거부하며, 작성자에게 종료 시각과 이의제기 경로를 표시한다. 만료 후에는 전송을 허용한다.

### 4.1 1차 필터 계약

Backend는 채팅을 저장하고 필터 결과·공개 범위를 결정한 뒤 SSE 이벤트를 발행한다. 가려야 할 원문을 먼저 전체에 보내고 화면에서 제거하는 방식으로 구현하지 않는다. 아래 수치는 개발 기본값이다.

| 결과 | 조건 | 표시 | Agent 전달 |
| --- | --- | --- | --- |
| PASS | 다른 조건에 해당하지 않음 | PUBLIC | 없음; 이후 신고되면 조사 가능 |
| REVIEW | 공격·비하 사전 매칭 또는 대상 지칭과 공격 표현 동시 등장 | PUBLIC | 사건에 묶어 조사 |
| HOLD | 공식 자칭 + 로그인·인증 요구 + 비공식 URL의 복합 조건 | HELD: 본인에게만 표시 | 우선 조사 |
| FLOOD | 같은 이용자·채널에서 10초 내 정규화된 동일 문장 3회 이상 | 세 번째부터 HELD | 하나의 도배 묶음으로 조사 |

동시 매칭 시 `HOLD > FLOOD > REVIEW > PASS` 순서로 대표 결과를 정하되 모든 매칭 태그를 보존한다. 공백 축약·유니코드 정규화·동일 문자 반복 축소를 적용한 동일 문장 비교로 시작하며, 의미 유사도 모델은 MVP에서 제외한다. 같은 `client_message_id` 재전송은 별개의 채팅·도배 횟수로 세지 않는다.

전화번호·계좌번호 노출을 독립 제재 유형으로 추가하지 않는다. 개인정보 토큰 마스킹은 세 위험 유형의 조사 과정 모두에 적용한다. 단순 비공식 URL만으로 HOLD나 위반을 확정하지 않는다.

### 4.2 사건 병합과 분석 시작

| 항목 | 규칙 |
| --- | --- |
| 기본 묶음 범위 | channel_id + user_id + 수집 창; 사용자·채널을 넘겨 합치지 않음 |
| REVIEW 수집 창 | 첫 후보 도착부터 3초, 종료 시 1회 분석 요청 |
| HOLD | 최초 후보부터 1초 이내 분석 요청; 후속 후보는 기존 사건에 연결하되 해당 메시지를 즉시 가림 |
| FLOOD 묶음 | 최초 3회 판정에 사용한 첫 메시지의 수신 시각 t0부터 [t0, t0+10초) 고정 창. 첫 두 메시지도 증거로 연결, 창 종료 시 1회 분석 |
| REVIEW→FLOOD | 분석 전 REVIEW 사건이면 같은 사건을 승격하고 도배 창으로 마감 시각 변경 |
| REVIEW→HOLD | 분석 전이면 같은 사건을 승격하고 HOLD가 감지된 시각부터 1초 이내 분석 |
| 분석 중 도착 | 기존 사건의 evidence_version을 증가시키고 dirty 표시. 분석 중인 스냅샷은 바꾸지 않음 |
| 종료 후 후보 | 새 사건을 만들되 기존 제재·진행 중 제한을 조회하고 동일 증거 재제재를 금지 |

증거가 추가되면 실행 직전 `expected_case_version`이 맞지 않아 오래된 조치 계획은 거부된다. 새 스냅샷으로 최대 1회 후속 분석하며, 그 뒤에도 계속 변경되면 신규 확정 조치 없이 예외 검토로 넘긴다. 늦게 도착한 메시지도 초기 가림 규칙은 즉시 적용한다. 동시 수신은 사용자·채널별 잠금 또는 DB 트랜잭션으로 직렬화하고 메시지-사건 연결을 중복 생성하지 않는다.

도배 시연은 t0부터 0.9초 간격으로 10개를 보내 모든 메시지가 한 10초 창에 들어가도록 고정한다. 이 조건에서는 사건 1건·최초 분석 1건을 기대한다. 분석을 시작한 뒤 10초 넘게 이어지는 트래픽까지 모두 한 사건이라고 주장하지 않는다.

### 4.3 위반 이력과 조치 횟수

- 위반 횟수는 메시지 수나 도구 호출 수가 아니라, 적용이 확인된 **사건별 위반 기록 1건**으로 센다.
- 같은 사건의 숨김·채팅 제한을 두 번의 위반으로 세지 않는다. 재시도·재조사도 횟수를 늘리지 않는다.
- 동일 근거 메시지를 다른 사건에서 다시 사용해 추가 제한하지 않는다. 메시지 ID 목록과 기존 조치 연결을 서버에서 검사한다.
- 취소된 위반은 가중 이력에서 제외한다. MVP는 이전 위반 횟수와 무관하게 자동 제한 상한을 5분으로 유지한다.
- 유효한 제한 중에는 새 TIMEOUT으로 만료를 연장하지 않고 기존 조치에 연결해 결과를 보고한다. 24시간·7일 자동 제재는 제외한다.

### 4.4 실행 가능한 판단 조건

`VIOLATION` + 실제 조회한 근거 메시지 + 유효한 정책 조항 1개 이상 + 조치 기준표 항목 + 최신 사건 버전이 모두 필요하다. Backend는 정책 버전·권한·대상·허용 기간을 재검증한다. 근거가 없거나 충돌하면 `NEEDS_REVIEW`로 보내며 모델 확신 점수만으로 실행하지 않는다.

## 5. 핵심 시연 시나리오

### 시나리오 A. 정상적인 표현의 오탐 방지

**입력**

> “와 오늘 무대 진짜 미쳤다ㅋㅋㅋㅋ”
> 
1. 1차 필터가 의심 표현을 감지해 조사 대상으로 전달한다.
2. Agent가 앞뒤 대화와 자체 정책의 정상 예외를 확인한다.
3. 특정인에 대한 공격이 아닌 긍정적 반응으로 판단한다.
4. 공개 상태면 그대로 두고, 임시 가림된 경우 서버 검증 후 자동 해제한다.
5. 판단 근거와 최종 공개 상태를 기록한다.

**기대 결과:** 정상 메시지는 제재하지 않으며, 초기 오탐이 발생했다면 공개 상태로 복구한다.

**검증 요소:** 맥락 분석, 정책 예외 검색, 정상 분기, 상태 확인.

### 시나리오 B. 반복적인 괴롭힘 — 채팅 제한 선조치·후보고

**입력**

> “너는 왜 맨날 그러냐. 방송 접어라.”
> 

같은 사용자가 같은 대상을 향해 비슷한 공격성 채팅을 여러 차례 작성한 상황을 가정한다. 단일 문장만으로 반복 괴롭힘을 확정하지 않는다.

**처리 과정**

1. 공격적 메시지를 탐지하고 초기 가림 규칙에 해당하면 해당 메시지를 임시 가림한다.
2. Agent가 최근 채팅, 공격 대상, 이전 제재 및 취소 이력을 조회한다.
3. 자체 운영정책에서 괴롭힘 정의·반복 기준·정상 예외·제한 기간을 검색한다.
4. 맥락과 반복 근거를 확인해 위반 여부를 판단한다.
5. Backend가 근거 ID, 정책 버전, 대상 채널, 허용 기간, 기존 조치 여부를 검증한다.
6. 자동 조치 요건이 충족되면 Business MCP로 **해당 채널의 한시적 채팅 제한을 즉시 실행**한다. 운영자 사전 승인은 기다리지 않는다.
7. DB의 제한 상태·종료 시각을 조회하고 실제 채팅 전송이 제한되는지 확인한다.
8. 운영자에게 근거와 실행 결과를 후보고하고 작성자에게 사유·기간·이의제기 방법을 안내한다.
9. 이의제기가 접수되면 운영자가 원문·맥락·정책·조치 이력을 재검토해 유지 또는 취소한다.

이번 기준표에 따라 해당 공격 메시지 숨김도 채팅 제한과 별도 조치 ID로 실행·확인한다. 한 조치만 성공했을 때 두 조치가 모두 완료된 것처럼 표시하지 않는다.

**기대 결과:** 제한이 자동으로 DB와 전송 API에 반영되고 보고·실행 이력이 남는다. 이의제기 인용 시 해당 제한을 해제하고 취소 이력을 기록한다.

**검증 요소:** Business MCP, RAG MCP, 자동 실행 요건 검증, 후보고, 이의제기 기반 HITL, 제한 만료·해제.

### 시나리오 C. 피싱 의심 링크 — 메시지 숨김 선조치·후보고

**입력**

> “공식 팬미팅 당첨 확인! 이 사이트에서 계정으로 로그인하세요.”
> 

시연 데이터에는 실제 접속하지 않는 외부 URL과 발신자 역할을 함께 구성한다.

**처리 과정**

1. 외부 URL·로그인 유도·공식 안내 자칭 표현을 감지한다.
2. 초기 복합 규칙에 해당하는 메시지를 임시 가림한다.
3. Agent가 방송 공식 이벤트 정보, 등록된 공식 주소, 발신자의 실제 역할을 조회한다.
4. 사칭·외부 계정정보 입력 유도 관련 자체 정책과 인용·공식 안내 예외를 검색한다.
5. 정책상 자동 숨김 요건이 확인되면 Backend 검증을 거쳐 Business MCP로 메시지를 숨김 처리한다. 운영자에게 사전 승인을 요청하지 않는다.
6. DB 상태와 다른 시청자의 실시간·이력 조회에서 비공개 여부를 확인한다.
7. 운영자에게 근거·조치 결과를 보고하고 작성자에게 사유·이의제기 경로를 안내한다.
8. 이의제기가 접수되면 운영자가 유지·취소를 결정하고, 취소 시 공개 상태로 복구한다.

**기대 결과:** 정책상 위험 요건을 충족한 메시지는 먼저 숨김 처리되고 결과가 보고된다.

**검증 요소:** 역할·공식 주소 조회, 정책 RAG, 자동 숨김, 공개 범위 검사, 사후 재검토.

URL 포함 또는 비공식 주소라는 사실만으로 피싱을 확정하지 않는다. 이 시나리오는 **자체 정책상 사칭·계정정보 입력 유도 위험에 대한 조치**이며, 사이트의 실제 악성 여부를 검증한 결과가 아니다. 근거가 부족하면 숨김 확정을 보류하고 예외 검토로 전달한다.

### 시나리오 D. 자동 조치 실행 실패 및 결과 불명

**상황**

Agent가 정책 요건을 확인하고 자동 채팅 제한 또는 메시지 숨김을 요청했지만, Business MCP나 내부 API에서 오류·시간 초과가 발생한다. 사전 운영자 승인은 전제하지 않는다.

**처리 과정**

1. 조치 ID와 중복 방지 키를 생성·저장하고 변경 도구를 호출한다.
2. 오류 종류, 요청 ID, 마지막 확인 상태를 기록한다.
3. 응답이 없으면 `UNKNOWN`으로 표시하고 같은 조치 ID로 실제 반영 여부를 조회한다.
4. 이미 반영됐으면 성공으로 확정하고 재실행하지 않는다.
5. 미반영이 확인된 일시 오류만 같은 중복 방지 키로 제한적으로 재시도한다.
6. 권한·정책·대상 버전 오류는 반복 실행하지 않고 재검토 대상으로 넘긴다.
7. 재시도 소진 후 미반영이 확인되면 `FAILED`로 기록한다. 끝까지 반영 여부를 확인할 수 없으면 `UNKNOWN`을 유지하며 운영자 확인 대상으로 보고한다.
8. 성공·실패·미확인 결과를 운영 콘솔에 표시한다. 보고 전송만 실패하면 조치를 다시 하지 않고 보고 작업만 재시도한다.

**기대 결과:** 실패나 미확인을 성공으로 표시하지 않고 중복 제재 없이 실제 상태를 복구·확인한다.

**검증 요소:** Harness Recovery, Observability, 상태 조회, 멱등성, 조치와 보고의 분리.

이미 임시 가림된 메시지는 분석·실행 오류만으로 자동 공개하지 않는다. 공개 메시지도 오류 자체를 이유로 가리지 않는다. 실패한 채팅 제한은 실제로 사용자를 제한했다고 표시하지 않으며, 기존 한시적 제한의 종료 시각도 실패 때문에 연장하지 않는다.

### 시나리오 E. 이의제기 재검토 및 오탐 복구

1. 작성자가 조치 내역에서 “공격 표현을 인용해 말린 내용”이라는 사유로 이의제기한다.
2. 본인·사건·조치 연결을 검증하고 재검토 작업을 만든다. MVP 이의제기는 조치별로 접수하며 같은 사건의 숨김과 제한도 각각의 조치 ID로 유지·취소한다.
3. Agent가 원래 판단 근거와 추가 맥락을 정리한 뒤 운영자 결정을 기다리며 상태를 저장한다.
4. 운영자가 유지 또는 취소와 사유를 입력한다.
5. 같은 재검토 작업의 `thread_id`로 재개하고 최신 상태·권한·결정 버전을 검증한다.
6. 유지면 결과를 기록하고, 취소면 해당 조치만 해제·복구한 뒤 결과를 확인한다.
7. 작성자에게 결과를 통지하고 원래 판단·취소·복구 이력을 함께 보존한다.

**기대 결과:** 최초 조치는 자동 실행하되 이의제기에는 사람의 판단과 상태 저장·재개가 실제로 적용된다. 취소된 제재는 이후 반복 위반 가중 근거에서 제외한다.

이미 제한이 만료되었어도 잘못된 제재 이력은 취소할 수 있다. 다른 사건에서 부과한 유효한 제한까지 함께 해제하지 않는다. 이의제기 접수만으로 자동 해제하거나 제한 기간을 연장하지 않는다.

## 6. RAG 및 데이터 활용 계획

### 6.1 정책 설계 참고 자료

외부 문서는 유형 정의와 운영 절차의 참고 자료이며 자체 정책의 자동 제재 수치를 뒷받침하는 근거로 사용하지 않는다. 실제 판정에는 자체 정책만 색인한다. 구현 시 참조한 조항·확인일을 정책 메타데이터에 남긴다. 아래는 기존 두 문서에서 공통적으로 활용한 자료이며 이번 통합에서 본문을 새로 검증한 목록은 아니다.

| 자료 | 설계에 반영할 영역 |
| --- | --- |
| [위버스 서비스 운영정책](https://weverse.io/policies/service?hl=ko) | 금지 행위 유형, 반복 위반·이의제기 절차 참고 |

티빙·쿠팡플레이 등 구체적으로 반영하지 않은 자료는 제외했다.

### 6.2 실제 적용 문서

| 문서 | 내용 | 파일명 예시 |
| --- | --- | --- |
| 커뮤니티 정책 | 유형 정의, 위반·정상 사례, 인용 예외 | `community_policy.md` |
| 자동 조치 정책 | 초기 가림, 숨김, 반복 기준, 제한 기간·상한, 자동 해제 | `moderation_policy.md` |
| 보안 위험 대응 | 공식 역할·주소, 사칭·외부 유도 조건 | `security_policy.md` |
| 사후 검토 매뉴얼 | 후보고, 이의제기, 유지·취소·복구, 실패 처리 | `moderation_manual.md` |

정책의 실행 규칙은 버전이 있는 단일 정책 설정을 원본으로 관리하고, `moderation_policy.md` 조치표와 Backend 기준표를 같은 설정에서 생성·대조한다. 문서와 서버 값이 다르면 해당 정책 버전의 실행을 차단한다. 정책 수치의 독립적인 이중 수정을 허용하지 않는다.

문서는 총 3~5쪽 내외로 시작하고 조항 단위로 색인한다. 조항 ID·제목·본문·버전·시행일·원문 URI를 반환한다. 채팅 원문은 정책 색인에 섞지 않는다. RAG의 판단 근거와 Backend의 실행 규칙은 같은 정책 버전을 참조해야 한다.

### 6.3 개발·평가용 정책 초안

아래 수치는 구현 가능한 예시이며, 실제 플랫폼의 정책이나 확정된 팀 합의가 아니다. 평가 시작 전 고정하고 기록한다.

| 유형 | 초기 선별·임시 가림 | 후속 자동 조치 요건·범위 |
| --- | --- | --- |
| 도배 | 같은 사용자가 같은 채널에서 10초 내 동일 정규화 문장 3회 전송 시 세 번째부터 임시 가림 | 재전송 ID 중복·정상 예외 제외 후 해당 메시지 숨김 |
| 반복 괴롭힘 | REVIEW로 공개 유지·조사; FLOOD/HOLD가 겹치면 해당 가림 규칙 우선 | 최근 5분 내 같은 대상에 대한 별개의 공격 발언 3건 이상을 맥락으로 확인하면 해당 채널 5분 제한 |
| 사칭·외부 유도 | 공식 자칭·로그인 요구·비공식 URL 복합 조건이면 임시 가림 | 실제 역할·공식 주소·맥락·정책을 확인해 위험 요건 충족 시 해당 메시지 숨김 |
| 정상 예외 | 인용·주의·긍정 반응 여부 조사 | `HELD` 메시지만 자동 공개; 이미 내려진 `HIDDEN` 조치의 취소는 운영자 재검토 |
| 근거 부족 | 추가 조회 후에도 불충분 | 신규 확정 제재 없이 예외 검토, 기존 가림 상태와 보류 이유 표시 |

채팅 제한은 MVP에서 5분을 상한으로 두며 모델이 임의로 늘리지 못하게 한다. 같은 증거를 재처리해 제한을 연장하지 않는다. 다른 사건과 겹친 제한은 조치별 종료 시각을 보존한다. 보류 사건은 검토 기한을 관리하며, 제안값은 접수 후 10분 이내 검토·기한 초과 알림이다. 한시적 제한은 명시한 만료 시각을 넘겨 유지하지 않는다.

### 6.3.1 자동 조치 기준표

| 유형 | 최근 30일 유효 위반 0건 | 1건 | 2건 이상 |
| --- | --- | --- | --- |
| 반복 괴롭힘 요건 충족 | 대상 메시지 숨김 + 해당 채널 5분 제한 | 동일 | 동일; 검토 우선순위만 상향 |
| 도배 확정 | 세 번째 이후 중복 메시지 숨김 | 동일 | 동일 |
| 사칭·외부 유도 위험 요건 충족 | 해당 메시지 숨김 | 동일 | 동일 |
| 단일 공격·근거 부족 | 자동 채팅 제한 없음, 필요 시 예외 검토 | 동일 | 동일 |

위반 이력은 맥락과 검토 우선순위에 사용한다. 이 표의 고정 상한을 넘는 자동 제재는 서버가 거부한다. 운영자가 더 강한 제재를 자유롭게 설정하는 기능은 MVP에 포함하지 않는다.

## 7. 시스템 아키텍처

### 7.1 전체 흐름

```
시청자 → Vue → POST → Spring Boot: 인증·채팅 저장·초기 규칙 검사
                         ├─ 일반 메시지 → SSE 공개
                         └─ 위험 후보 → 해당 메시지 임시 가림·사건 저장
                                            ↓
                                   RabbitMQ → Worker
                                            ↓
                                  FastAPI + LangGraph
                                    ├─ Business MCP → 내부 업무 API
                                    └─ RAG MCP → PostgreSQL·pgvector
                                            ↓
                                  판단·정책 근거·조치 결정
                                            ↓
                         Backend의 정책·권한·버전·중복 검증
                                            ↓
                                 자동 조치 → 실제 상태 확인
                                            ↓
                            운영자 후보고 / 작성자 조치 안내
                                            ↓
                         이의제기 → 운영자 재검토 → 유지·취소
                                            ↓
                                 필요 시 복구 → 결과 통지
```

일반 채팅은 LLM 완료를 기다리지 않는다. 조건에 맞는 후보만 먼저 가리고 비동기 조사한다. 초기 규칙이 놓친 내용은 공개될 수 있으므로 모든 유해 채팅의 사전 차단을 보장하지 않는다.

### 7.2 기술·책임

| 구성 | 기술 | 책임 |
| --- | --- | --- |
| 화면 | Vue 3·TypeScript | 채팅, 본인 조치·이의제기, 관제 콘솔 |
| 업무 서버 | Spring Boot | 인증·공개 범위·정책 실행 규칙·DB 변경 |
| 실시간·알림 | POST + SSE | POST 채팅 전송, SSE 채팅 수신·사건 알림 |
| Agent | Python FastAPI·LangGraph | 선택 조회·추가 조사·근거 연결·상태 저장 |
| MCP | FastMCP | 업무 API 연결, 검색·원문 Resource |
| DB·RAG | PostgreSQL·pgvector | 업무·작업 상태, 자체 정책 색인 |
| 대기열 | RabbitMQ·Worker | 조사·재개·재시도·보고 작업 |
| 실행 환경 | Docker Compose | 서비스 통합 실행 |
| AI 호출 | OpenAI API | 모델·임베딩 설정을 환경변수로 관리 |

모델명은 이 문서에서 새로 확정하지 않으며 구현 환경에서 검증한 값을 평가 기록에 남긴다. API 비밀키는 화면이나 저장소에 넣지 않는다.

### 7.3 데이터·API 계약

| 데이터 | 핵심 내용 |
| --- | --- |
| 메시지 | 작성자·채널·원문·공개 상태·버전 |
| 사건 | 유형·증거 참조·조사 상태·정책 버전 |
| 조치 | 조치 ID·대상·사유·시작/종료 시각·실행 결과·중복 방지 키 |
| 보고 | 조치 결과·운영자 전달 상태·작성자 통지 상태 |
| 이의제기 | 조치 ID·신청자·사유·검토자·결정·복구 결과 |
| 작업 | task/thread/trace ID·체크포인트·재시도 예산 |

API·SSE·MCP·State의 구현 기준은 부록 A를 따른다. 최초 자동 조치에는 승인 API를 요구하지 않는다.

### 7.4 배포·인증 경계

시연 환경은 frontend:80과 backend:8080만 호스트에 공개한다. Agent·MCP·PostgreSQL·RabbitMQ는 내부 네트워크에 둔다. 브라우저는 frontend의 `/api` 프록시를 통해 같은 출처로 접근한다. 외부 배포 시 HTTPS를 적용하고 내부 경로 `/internal/**`는 공개 프록시·외부 커넥터에서 차단한다. 내부 API는 별도 서비스 토큰과 업무 권한을 검사한다.

| 서비스 | 내부 포트 예시 | 호스트 공개 |
| --- | --- | --- |
| frontend | 80 | 예 |
| backend | 8080 | 예; 외부 라우트만 제공 |
| agent | 8000 | 아니오 |
| business-mcp / rag-mcp | 9101 / 9102 | 아니오 |
| PostgreSQL·pgvector | 5432 | 아니오 |
| RabbitMQ | 5672 | 아니오; 관리 UI는 시연 시 localhost에 한시 연결 |

별도 Chroma 서비스는 사용하지 않는다. 업무·체크포인트·벡터는 PostgreSQL 안에서 테이블·스키마를 구분한다. Agent는 업무 테이블을 직접 변경하지 않고 자신의 체크포인트만 저장한다.

### 7.5 ISO/IEC 25010 품질 특성 대응

[ISO/IEC 25010:2023 공식 안내](https://www.iso.org/standard/78176.html)의 제품 품질 모델을 참고해 프로젝트에 직접 적용할 특성을 선택했다. 아래 표는 일부 특성의 설계·검증 대응이며 전체 표준 적합성이나 인증을 의미하지 않는다. 수업 자료가 다른 판본을 사용하면 제출 시 명칭을 대조한다.

| 품질 특성 | 설계 결정 | 검증 증거 |
| --- | --- | --- |
| 기능 적합성 | 자체 정책·정상/위반/보류·사후 정정 | Baseline 대비 판단·조치·근거 평가 |
| 성능 효율성 | 채팅과 분석 분리, 필터 선별, 사건 병합 | 최초 가림 지연·분석 횟수·p50/p95 |
| 신뢰성 | 체크포인트·결과 불명 조회·재시도·DLQ·멱등성 | 재시작·응답 유실·중복 전달 시험 |
| 보안성 | 역할·채널 권한, 내부 API 보호, 마스킹, 도구 범위 제한 | 타 채널 접근·원문 노출·지시문 삽입 시험 |
| 유지보수성 | 업무 규칙 서버 집중, 정책 버전·공통 계약, MCP 분리 | 정책 불일치 차단·계약 검증·교체 가능한 Dispatcher |

상태 저장과 접근 제어가 있다는 사실만으로 품질 목표를 달성했다고 표현하지 않고 실제 시험 결과를 첨부한다.

## 8. AI Agent 설계

### 8.1 최초 조치 Graph

```
사건 로드 → 필요한 조사 도구 선택 → 정책 검색 → 근거 충분성 검사
  ├─ 부족 → 예산 내 추가 조회 → 여전히 부족하면 예외 검토
  ├─ 정상 → 공개 유지 또는 임시 가림 해제 → 기록
  └─ 위반·자동 조치 대상
       → Backend 실행 요건 검사
       → 자동 실행
       → 결과 조회
          ├─ 성공 → 후보고·작성자 안내 → 완료
          ├─ 미반영 일시 오류 → 같은 조치 ID로 제한 재시도
          └─ 실패/결과 불명 → 상태 기록·운영자 예외 처리
```

도배는 간격·중복 전송, 괴롭힘은 대상·대화·반복, 사칭은 실제 역할·공식 주소를 우선 조회한다. 모든 사건에 같은 조회 목록을 무조건 실행하지 않는다.

### 8.2 이의제기 Graph와 State

```
이의제기 접수 → 기존 조치·추가 맥락 조회 → 검토 자료 작성
    → REVIEW_PENDING: 체크포인트 저장·운영자 결정 대기
    → 같은 재검토 thread_id로 재개
    → 권한·결정 버전·최신 조치 상태 재검증
       ├─ 유지 → 사유 기록·통지
       └─ 취소 → 해당 조치 복구 → 실제 상태 확인 → 결과 통지
```

이의제기 Graph는 최초 실행 기록을 연결한 별도 재검토 작업으로 만든다. 최초 작업을 모든 이용자의 이의제기를 기다리며 무기한 중단하지 않는다.

| State | 내용 |
| --- | --- |
| `case_id`, `task_id`, `thread_id`, `trace_id` | 사건·실행 추적 |
| `message_ids`, `channel_id`, `user_id` | 사건의 메시지 목록과 접근 범위 |
| `evidence_refs`, `evidence_version` | 실제 조회한 근거·버전 |
| `policy_evidence`, `policy_version` | 적용 조항·버전 |
| `judgment`, `requested_actions`, `action_plan` | 판단·요청 조치·서버 검증 계획 |
| `idempotency_keys` | action_plan 안의 action_id별 중복 방지 키 |
| `execution_results`, `notification_status` | 조치별 결과와 보고 상태 |
| `appeal_id`, `decision_id`, `review_decision` | 이의제기·서버에 저장된 운영자 결정 |
| `turn_count`, `retry_count` | 조사 턴·재시도 예산 |
| `filter_result`, `case_version`, `dirty` | 필터 분류·증거 스냅샷·추가 메시지 여부 |

판단은 `VIOLATION / NO_VIOLATION / NEEDS_REVIEW`, 실행은 `PENDING / RUNNING / SUCCEEDED / FAILED / UNKNOWN`, 이의제기는 `OPEN / REVIEW_PENDING / UPHELD / OVERTURNED`로 구분한다. 취소 결정과 복구 실행 성공 여부도 별도로 표시한다.

### 8.2.1 작업 ID와 도구 선택

`case_id`는 사건을 식별하고 `task_id`는 작업, `thread_id`는 체크포인트 실행을 식별한다. 최초 조사는 `case:{case_id}:analysis:{revision}`, 이의제기는 `case:{case_id}:appeal:{appeal_id}`로 구분한다. 재시도·운영자 결정 후 재개에는 해당 작업의 같은 thread_id를 사용한다. 중복 요청이 새 Graph를 만들지 않도록 task_id와 큐 event_id도 검사한다.

| 단계 | 결정 주체 |
| --- | --- |
| load_case·mask_input | 코드 |
| investigate | 모델이 조회 도구·인자를 선택, 관찰 후 추가 조회 여부 결정 |
| judge | 모델의 구조화 판단 |
| validate_action·execute·verify | 코드와 Backend 업무 규칙 |
| 이의제기 유지·취소 | 담당 운영자 |

investigate에는 조회·검색 도구만 노출한다. 변경 도구는 서버가 허용한 action plan을 코드 실행 노드가 호출한다. 도배는 맥락 조회와 정책 검색, 괴롭힘은 맥락·이력·정책, 사칭은 역할·공식 주소·정책 중심으로 선택한다. 모든 유형에 정책 근거는 필수지만 조회 도구와 순서는 달라질 수 있다. trace로 선택 차이를 검증한다.

### 8.3 출력 검증

구조화된 출력에 판단, 유형, 조치, 근거 메시지 ID, 정책 조항 ID, 짧은 이유, 부족한 정보를 포함한다. 서버는 실제 조회한 근거인지, 해당 정책 버전이 유효한지, 기간과 대상이 허용 범위인지 검사한다. 모델이 제시한 확신 점수만으로 실행하지 않는다.

| `hide_message` | 변경 | 정책 요건이 검증된 메시지 자동 숨김 |
| `timeout_user` | 변경 | 정책 범위의 한시적 채팅 제한 |
| `release_message` | 변경 | 정상 확인된 임시 가림 해제 또는 운영자 취소 결정에 따른 공개 |
| `revoke_timeout` | 변경 | 운영자 취소 결정에 연결된 특정 제한 해제 |

변경은 반드시 Spring Boot 내부 API에서 처리한다. 자동 실행에는 정책 기반 실행 자격을, 이의제기 취소에는 서버에 저장된 운영자 결정을 검증한다. 모델이 보낸 `approved=true` 같은 값은 권한으로 사용하지 않는다.

도구별 설명·입출력·오류 코드·시간 제한을 정의한다. 채널·대상 범위를 서버에서 검사하고, 상태 변경·조치 이력·보고 발행 대기 기록을 가능한 한 같은 DB 트랜잭션에 저장한다. 동일 키 재요청은 기존 결과를 반환한다.

### 9.2 RAG MCP

| 기능 | 역할 |
| --- | --- |
| `search_policy` | 정의·예외·자동 조치 조건 검색 |
| `get_policy_section` | 특정 조항 확인 |
| `policy://{version}/{document_id}/{section_id}` | 원문 Resource |

검색 결과에 조항 ID·제목·본문·버전·시행일·원문 URI를 포함한다. 운영자는 조사에 사용한 정책 원문을 열어 볼 수 있어야 한다.

### 9.3 조치 ID·멱등성·트랜잭션

사건당 조치 종류 하나라는 제약만으로는 여러 메시지의 숨김·복원과 이의제기를 구분할 수 없다. Backend가 논리 조치마다 action_id를 발급한다. 모델·브라우저가 키를 임의로 생성해 실행 자격을 만들 수 없다.

| 조치 | 논리 유일성 |
| --- | --- |
| HIDE | case_id + HIDE + message_id |
| TIMEOUT | case_id + TIMEOUT + channel_id:user_id |
| RELEASE_HELD | case_id + RELEASE_HELD + message_id |
| RESTORE_MESSAGE / REVOKE_TIMEOUT | review_decision_id + action_type + original_action_id |

`actions.idempotency_key`와 위 논리 범위에 UNIQUE 제약을 둔다. 키는 `action:{action_id}`이며 같은 키에 다른 요청 내용이 오면 409 `IDEMPOTENCY_CONFLICT`로 거부한다. 같은 요청 재실행은 저장된 결과를 반환한다. 실패 기록이 있다는 이유로 성공 결과를 반환하지 않고, 재시도 가능한 상태인지 검사한다.

메시지별 HIDE를 각각 기록한다. 향후 묶음 요청을 추가해도 결과를 개별 반환한다. MVP는 메시지별 호출을 기본으로 한다. 같은 계획의 여러 조치는 서버가 계획·대상별 버전을 추적한다. 첫 조치의 정상 상태 변경 때문에 다음 조치가 자신의 계획을 오래된 것으로 오인하지 않도록 처리하며 외부 증거 변경은 별도로 검출한다. 상태 변경·조치 결과·후보고 outbox 기록은 한 트랜잭션으로 처리한다. TIMEOUT의 종료 시각은 최초 성공 시 저장한 값이며 재시도에서 다시 계산하지 않는다.

UNKNOWN은 먼저 action_id로 조회한다. 미반영 확인은 처리 중인 동일 키 요청이 없음을 포함해 서버가 판정한다. 네트워크 오류나 404 하나만으로 실패를 확정하지 않는다. 취소도 원래 조치 ID와 결정 ID에 묶어 재시도하며 관련 없는 제한·가림을 해제하지 않는다.

## 10. Harness 및 안전장치

### 10.1 실행 관리

| 구성 | 적용 방법 |
| --- | --- |
| Instructions | 자체 정책 준수, 근거 부족 시 보류, 자동 조치 범위 명시 |
| Tools | 허용 도구, 형식·권한·최신 상태·중복 검사 |
| Context | 필요한 대화만 제공, 개인정보 최소화, 결과 크기 제한 |
| State·Memory | 조사·이의제기 작업별 체크포인트·재개 |
| Agent Loop | 모델 호출 최대 8회, 조사 도구별 최대 3회, 활성 실행 120초를 초기 제안값으로 설정 |
| Guardrails | 근거 ID·정책 버전·조치 기간 검사, 채팅 속 지시문 무시 |
| Recovery | 결과 불명 조회, 일시 오류만 재시도, 복구 작업도 중복 방지 |
| Observability | 도구·시간·토큰·조치·보고·취소 이력 추적 |

최초 제재는 자동 실행한다. **HITL은 이의제기 재검토와 근거 부족·실패 예외 처리에 적용**한다. 운영자의 결정 대기 시간은 활성 실행 제한에서 제외한다. 조사 도구 호출 예산과 변경 도구 재시도 예산을 분리하며, 변경 도구는 최초 실행 이후 최대 2회 재시도로 제한하는 안을 사용한다.

### 10.2 인증

Spring Security 세션 쿠키를 사용하고 브라우저 채팅·관제 수신은 기본 EventSource를 사용한다. 동일 출처 프록시에서 HttpOnly·SameSite=Lax 쿠키를 사용하며 HTTPS 환경은 Secure를 적용한다. 변경 API는 CSRF 토큰을 헤더로 검증하고 로그인 후 세션을 회전한다. URL에 인증 토큰을 넣지 않는다. 로그인 해제·세션 만료·권한 회수 시 열린 SSE 연결도 종료하고 재접속 권한을 검사한다.

| 역할 | 권한 |
| --- | --- |
| VIEWER | 채팅·신고·본인 조치 조회·본인 이의제기 |
| MODERATOR | 담당 채널 사건·근거 조회, 재검토·취소 결정 |
| PLATFORM_ADMIN | 역할·채널 권한·정책 설정 관리 |
| 서비스 계정 | 인증된 내부 API를 통해 허용된 자동 조치 실행 |

클라이언트 역할값을 신뢰하지 않는다. 타 채널 이력 조회, 타인의 이의제기 제출, 일반 사용자 토큰으로 내부 변경 API 호출을 차단한다.

### 10.3 대기열·보고·실패

사건과 발행 대기 작업을 DB에 함께 저장한 뒤 RabbitMQ로 전달한다. Worker는 결과·체크포인트 저장 후 작업 완료를 알린다. 조사·재개·보고 재시도는 작업 종류를 구분하고 최종 실패 큐를 둔다. 메시지에는 ID·버전 중심으로 담고 인증 토큰은 넣지 않는다.

운영자 결정 대기 중에는 Worker를 점유하지 않는다. 결정을 저장하면 재개 작업을 발행한다. SDK·Agent·Worker가 각자 재시도 횟수를 늘리지 않도록 하나의 실행 예산을 공유한다.

조치 성공과 보고 성공을 구분한다. 조치 성공 후 알림만 실패했다면 보고만 재전송한다. 이벤트에 ID·버전을 넣어 중복·역순 도착을 처리하고, 재접속하면 DB의 최신 상태를 조회한다. 미확인 조치는 자동으로 성공·실패라고 단정하지 않고 운영자의 상태 확인 대상으로 남긴다.

### 10.4 유형 토큰 마스킹

| 원문 유형 | 모델에 전달할 표현 |
| --- | --- |
| 전화번호 / 이메일 / 계좌번호 | [PHONE] / [EMAIL] / [ACCOUNT] |
| URL | [URL:정규화된_호스트]; 경로·쿼리·토큰 제거 |
| 출연자 / 시청자 이름 | [STREAMER_1] / U1 등 사건 안에서 일관된 가명 |

마스킹은 최초 채팅뿐 아니라 모든 조회 도구 결과와 모델 trace 입력에도 적용한다. 원문은 공개 범위에 따라 고객사 채팅 화면에 표시되며, 관제 원문 조회는 담당 운영자로 제한한다. 일반 로그에는 원문을 기록하지 않는다. 공식 도메인 여부는 Backend가 URL 파서로 정규화한 호스트를 정확히 비교하며 부분 문자열 포함 여부로 판단하지 않는다. 모델에는 `is_official` 등 서버 검증 결과를 함께 전달한다. 토큰 치환만으로 익명성이 완전히 보장된다고 가정하지 않는다.

### 10.5 HTTP·RabbitMQ 공통 실행

Backend에 `TaskDispatcher`를 두고 `HttpTaskDispatcher`, `RabbitTaskDispatcher`를 같은 명세로 구현한다. Agent는 HTTP 수신부와 큐 consumer가 같은 `run_case(task_id)`·`resume_review(task_id)`를 호출한다. 두 경로 모두 outbox에서 작업을 발행하고 task_id 중복 실행을 검사한다.

Day 1은 HTTP 경로로 연결하고 Day 2에 RabbitMQ를 기본 경로로 전환한다. RabbitMQ는 최종 목표에 포함하며 HTTP 경로는 통합 장애 진단용으로 유지한다. 자동 fallback으로 두 경로를 동시에 발행하지 않는다.

| 큐 | 용도 |
| --- | --- |
| guard.analyze.urgent | HOLD 사건 조사 |
| guard.analyze | REVIEW·FLOOD 조사 |
| guard.resume | 운영자 결정 후 재검토 재개 |
| guard.notify | 후보고·작성자 통지 |
| guard.retry.10s / guard.retry.30s | 공유 예산 내 지연 재시도 |
| guard.dlq | 재시도 소진·운영자 확인 |

우선 큐에 별도 consumer를 두되 완료 순서를 보장한다고 표현하지 않는다. 작업 결과·체크포인트를 저장한 뒤 ACK한다. 운영자 대기 상태도 저장 후 ACK하며 사람을 기다리는 동안 worker를 점유하지 않는다. 최초 실행 후 추가 재시도 2회는 SDK·Graph·Worker 전체의 공유 예산이며 중첩 재시도로 늘리지 않는다. 보고 작업은 별도 예산으로 재시도한다.

## 12. 개발 일정

- Day 0에 고정한 정책·상태·이의제기 계약으로 구현 시작.

### DAY 3 — 실패 검증·평가·시연

- 미반영 실패, 실행됐지만 응답 유실, 보고만 실패하는 상황 재현.

- 정상·위반·보류 평가, 타 채널 접근·공개 범위 검증.
- A~E 시나리오의 실행 증거·평가 결과·예비 시연 영상 준비.

**완료 기준:** 자동 조치·후보고·이의제기 복구·중복 방지·결과 불명 처리를 반복 시연한다.

시간이 부족하면 통계·화면 장식·신고 고도화부터 줄인다. 이번 변경의 핵심인 자동 조치, 결과 확인, 이의제기와 취소 복구는 유지한다.

## 13. 성능 및 품질 평가 계획

### 13.1 비교 방식

같은 사례에 규칙만 적용한 결과, 메시지·정책만 제공한 판단, Agent가 맥락·이력·역할을 조회한 판단을 비교한다. 초기 가림 성능과 후속 AI 판단·조치 품질을 분리한다. 조사 대상으로 선별된 사례만으로 전체 채팅의 탐지율을 주장하지 않는다.

### 13.2 지표

| 지표 | 측정 방법·통과 조건 |
| --- | --- |
| 초기 탐지 | 전체 입력 기준 탐지율·정상 임시 가림률 |
| 판단 품질 | 위반·정상·보류 분류, 유형별 오탐·미탐 |
| 근거 정확성 | 실제 조회 메시지·올바른 정책 조항 여부 |
| 조치 적절성 | 기대 조치·채널·기간과 실제 실행 결과 비교 |
| 반응 속도 | 입력→초기 가림, 입력→자동 조치, 실행→후보고 지연 분리 |
| 실행 성공률 | 실행 요건을 통과한 요청 중 실제 반영이 확인된 비율, UNKNOWN 별도 집계 |
| 정정 품질 | 이의제기 취소 후 해당 조치 해제·공개 복구 성공 여부 |

## 부록 A. 구현 인터페이스 계약 v0.3

이 부록의 이름·필드는 구현 기본 계약이다. 모든 ID는 문자열 UUID, 시각은 UTC ISO 8601 문자열, 화면 표시는 Asia/Seoul로 변환한다. JSON은 camelCase를 사용하고 Python 내부 State의 snake_case와 경계에서 명시적으로 매핑한다. 사건·메시지·조치의 version은 1부터 증가하는 정수다. 목록의 기본 limit은 20, 최대 100이다.

### A.1 공통 응답·권한

```json
{
  "data": {},
  "traceId": "uuid"
}
```

오류 응답은 아래 구조를 사용한다. 입력 오류 400, 미인증 401, 미인가·채팅 제한 403, 미존재 404, 버전·멱등성 충돌 409, 업무 요건 미충족 422, 일시 장애 503을 구분한다. 오류만으로 변경이 미반영됐다고 추정하지 않는다.

```json
{
  "error": {
    "code": "STALE_VERSION",
    "message": "사건 정보가 갱신되어 재조회가 필요합니다.",
    "retryable": false,
    "actionId": null,
    "currentVersion": 4
  },
  "traceId": "uuid"
}
```

VIEWER는 본인 데이터, MODERATOR는 담당 채널, PLATFORM_ADMIN은 관리 권한 범위에서 접근한다. URL·body의 userId를 신뢰하지 않고 로그인 계정 또는 서버가 연결한 사건에서 대상을 확인한다. 원문·trace 상세는 담당 운영자에게만 노출한다.

### A.2 브라우저 REST API

아래 표의 `?`는 선택 필드다. 별도 표시 없는 필드는 필수다. 변경 API는 세션·CSRF 검증을 적용한다.

| Method·Path | 요청 | 성공 응답 data | 권한 |
| --- | --- | --- | --- |
| GET `/api/auth/csrf` | 없음 | `{token}` | 로그인 전 포함 |
| POST `/api/auth/login` | `{username,password}` + CSRF | `{userId,role,channelIds}` + 세션 쿠키 | 테스트 계정 |
| POST `/api/auth/logout` | 없음 | 204 | 로그인 |
| POST `/api/channels/{channelId}/messages` | `{clientMessageId,text,replyToId?}`; text 1~500자 | 201 `{messageId,visibility,version,sentAt}` | 해당 채널 VIEWER 이상 |
| GET `/api/channels/{channelId}/messages` | `cursor?&limit?` | `{items:[MessageView],nextCursor}` | 채널 접근 권한 |
| GET `/api/me/actions` | `cursor?` | `{items:[OwnAction],nextCursor}` | 본인 |
| GET `/api/cases` | `channelId&status?&cursor?` | `{items:[CaseSummary],nextCursor}` | 담당 운영자 |
| GET `/api/cases/{caseId}` | 없음 | `CaseDetail` | 담당 운영자 |
| GET `/api/tasks/{taskId}` | 없음 | `{taskId,caseId,status,stage,result?,error?}` | 담당 운영자 |
| POST `/api/actions/{actionId}/appeals` | `{clientRequestId,reason}`; reason 1~1000자 | 201 `{appealId,caseId,status:"OPEN",version}` | 해당 조치 대상 본인 |
| GET `/api/appeals/{appealId}` | 없음 | `AppealView` | 신청자·담당 운영자, 필드 차등 |
| POST `/api/appeals/{appealId}/decision` | `{decision:"UPHOLD" 또는 "OVERTURN",reason,expectedVersion,clientRequestId}` | 202 `{decisionId,taskId,status:"QUEUED"}` | 담당 운영자 |
| POST `/api/cases/{caseId}/retry` | `{taskId,expectedVersion,reason,clientRequestId}` | 202 `{taskId,status}` | 담당 운영자 |
| POST `/api/cases/{caseId}/manual-decision` | `{decision:"NO_CHANGE" 또는 "RELEASE_HELD" 또는 "APPLY_POLICY",actionType?,messageIds?,policyIds,reason,expectedVersion,clientRequestId}` | 202 `{decisionId,taskId}` | 담당 운영자 |
| POST `/api/reports` | `{messageId,reason,clientRequestId}` | 202 `{reportId,caseId}` | 채널 VIEWER 이상; 기본 기능 뒤 구현 |

`clientMessageId`는 `(channelId,userId,clientMessageId)` 유일성으로 재전송을 제거한다. 같은 ID·다른 text는 409, 같은 요청은 기존 응답을 반환한다. 제한 중 POST는 403 `CHAT_RESTRICTED`와 본인의 `until`을 반환한다.

`clientRequestId`가 있는 변경 요청은 사용자·엔드포인트·ID별로 중복 제거한다. 같은 조치의 열린 이의제기는 한 건만 허용한다. 이의제기 본문은 조회 화면에서 안전하게 이스케이프한다.

수동 예외 처리도 정책 상한을 넘을 수 없다. `APPLY_POLICY`는 실제 근거 메시지·유효 정책·기준표를 모두 검사한다. 최초 자동 조치 경로와 별개의 예외 경로다. UNKNOWN 재처리는 새 조치부터 만들지 않고 기존 조치 상태를 조회한다.

| 응답 타입 | 필드 |
| --- | --- |
| MessageView | `messageId,channelId,authorAlias,text,visibility,version,sentAt`; HELD/HIDDEN 원문은 작성자·담당 운영자에게만 |
| OwnAction | `actionId,type,status,reason,policySummary,startedAt,expiresAt?,appealId?,version`; 타인의 이력 제외 |
| CaseSummary | `caseId,channelId,subjectAlias,status,filterResult,messageCount,version,createdAt` |
| CaseDetail | CaseSummary + `messages,evidenceRefs,policySnapshots,judgment,actions,tasks,appeals`; 원문은 담당 권한 검사 |
| AppealView | `appealId,actionId,status,reason,decisionReason?,restorationStatus?,version`; 내부 근거·trace는 운영자에게만 |

### A.3 SSE 구독·이벤트

| 경로 | 수신자 |
| --- | --- |
| GET `/api/channels/{channelId}/events` | 해당 채널 시청자·운영자 |
| GET `/api/guard/events?channelId={id}` | 담당 운영자 |
| GET `/api/me/events` | 본인 조치·이의제기 알림 |

같은 출처의 EventSource·세션 쿠키를 사용한다. 서버는 이벤트 발행 시에도 수신자 권한과 메시지 공개 범위를 적용한다. 15초마다 heartbeat 주석을 보내고 프록시 버퍼링을 해제한다. 세션 만료·로그아웃은 연결을 종료한다.

각 이벤트는 SSE `id`, `event`, `data`를 포함한다. data 공통 필드는 `eventId,occurredAt,entityVersion,payload`다. 이벤트 ID는 스트림 안에서 재개 가능한 서버 순번을 사용한다. 최근 10분 이벤트를 보존하는 기본안으로 시작하고 `Last-Event-ID` 이후를 권한에 맞게 재전달한다. 보존 범위 밖이면 `RESYNC_REQUIRED`를 보내고 클라이언트가 이력 API로 재동기화한다.

```
id: 182
event: ACTION_APPLIED
data: {"eventId":"182","occurredAt":"2026-10-19T03:00:00Z","entityVersion":2,"payload":{"caseId":"uuid","actionId":"uuid","type":"TIMEOUT","status":"SUCCEEDED","expiresAt":"2026-10-19T03:05:00Z"}}
```

클라이언트는 eventId 중복을 제거하고 엔티티별 오래된 version을 무시한다.

| event | 추가 payload | 공개 범위 |
| --- | --- | --- |
| CHAT | `{messageId,channelId,authorAlias,text,visibility,sentAt}` | PUBLIC은 채널, HELD/HIDDEN은 본인·담당 운영자만 |
| MESSAGE_VISIBILITY_CHANGED | `{messageId,visibility}` | 이미 PUBLIC이었던 메시지의 화면 제거에는 ID만 전송 |
| MESSAGE_RESTORED | `{messageId,authorAlias,text,sentAt}` | 서버가 PUBLIC을 확인한 뒤 채널에 전달 |
| CASE_CREATED | `{caseId,filterResult,messageCount}` | 운영자 |
| CASE_STATUS | `{caseId,status,caseVersion}` | 운영자 |
| TOOL_START / TOOL_END | `{caseId,taskId,tool,callId,status?,elapsedMs?}` | 운영자; 원문 인자·내부 추론 제외 |
| ACTION_APPLIED | `{caseId,actionId,type,status,expiresAt?}` | 운영자·조치 대상 본인 |
| REVIEW_REQUIRED | `{caseId,appealId?,taskId,reasonCode}` | 운영자; 최초 자동 조치 승인 요청으로 사용하지 않음 |
| APPEAL_RESOLVED | `{appealId,decision,restorationStatus,reason}` | 본인·운영자 |
| DONE | `{caseId,taskId,actionIds,notificationStatus}` | 운영자 |
| FAILED | `{caseId,taskId,stage,errorCode,actionIds}` | 운영자 |
| ACTION_UNKNOWN | `{caseId,actionId,nextStep:"RECONCILE"}` | 운영자 |
| RESYNC_REQUIRED | `{resource:"messages" 또는 "cases" 또는 "me"}` | 해당 구독자 |

최초 HELD 원문은 다른 시청자에게 CHAT으로 보내지 않는다. 클라이언트 화면 숨김만으로 접근 제어를 구현하지 않는다. 운영자용 DONE이 발생해도 개별 조치·통지 상태를 표시하며 보고 실패를 제재 실패로 합치지 않는다.

### A.4 내부 API와 작업 전달

내부 API는 서비스 인증과 사건·채널 범위를 검사한다. 다음 경로는 브라우저에 공개하지 않는다.

| Method·Path | 요청 / 응답 |
| --- | --- |
| GET `/internal/cases/{caseId}` | 사건 스냅샷·버전·연결 메시지·판단·조치 |
| GET `/internal/cases/{caseId}/context?before=10&after=10` | 사건 범위의 맥락; 합계 최대 20건 |
| GET `/internal/cases/{caseId}/user-history?days=30` | 해당 채널의 유효·취소 제재, 최근 메시지 참조 |
| GET `/internal/cases/{caseId}/stream-info` | 공식 이벤트·도메인 |
| GET `/internal/cases/{caseId}/role` | 실제 작성자 역할 |
| GET `/internal/cases/{caseId}/official-links` | 정규화된 공식 호스트·판정 |
| POST `/internal/cases/{caseId}/plans` | `{expectedCaseVersion,judgment,evidenceMessageIds,policyVersion,policyIds,requestedActions}` → 검증된 `{planId,actions:[ActionCommand]}` |
| POST `/internal/actions/{actionId}/execute` | ActionCommand + Idempotency-Key → ActionResult |
| GET `/internal/actions/{actionId}` | ActionResult, 진행 중이면 상태 포함 |
| POST `/internal/review-decisions/{decisionId}/plans` | `{expectedCaseVersion}` → 권한·결정·원조치 검증 후 취소/수동 계획 |
| POST `/internal/tasks/{taskId}/events` | 이벤트 공통 구조; 서비스·task 연결 검사 후 저장·중계 |
| POST `/internal/tasks/{taskId}/result` | `{expectedTaskVersion,status,judgment?,actionResults?,checkpointRef?,error?}` → 저장 확인 |
| POST `/agent/tasks/{taskId}/run` | 작업 envelope → 202 `{taskId}` |
| POST `/agent/tasks/{taskId}/resume` | 작업 envelope → 202 `{taskId}` |

`requestedActions`는 모델 제안이며 실행 권한이 아니다. Backend가 대상·조항·정책 수치·기간·증거·현재 상태를 검증해 actionId를 발급한다. `/execute`는 body가 저장된 계획과 일치하는지 재검증한다. 정책 버전이나 대상 상태가 달라졌으면 새 계획이 필요하다.

HTTP·큐 공통 작업 envelope:

```json
{
  "eventId": "uuid",
  "taskId": "uuid",
  "caseId": "uuid",
  "kind": "ANALYZE",
  "threadId": "case:uuid:analysis:1",
  "expectedCaseVersion": 3,
  "decisionId": null,
  "attempt": 0,
  "traceId": "uuid"
}
```

kind는 `ANALYZE / REANALYZE / RESUME_REVIEW / NOTIFY / RECONCILE`다. decisionId는 RESUME_REVIEW일 때 필수다. 이벤트의 attempt 값을 신뢰해 예산을 늘리지 않고 DB 사용량으로 검사한다. 채팅 원문·인증 토큰은 큐에 넣지 않는다.

### A.5 MCP 도구 입출력

모든 도구 입력은 아래 필드만 허용하고 알 수 없는 필드는 거부한다. UUID는 문자열, before/after/days/topK는 정수다. 조회 도구는 caseId에 연결된 사용자·채널을 서버가 결정하므로 임의 userId로 바꿀 수 없다. optional 표기 외 필수다.

| 도구 | 입력 | output data |
| --- | --- | --- |
| get_moderation_case | `{caseId}` | `{caseId,channelId,userAlias,caseVersion,filterResult,messageIds,visibilityByMessage,judgment?,actions}` |
| get_chat_context | `{caseId,before?:10,after?:10}` | `{caseVersion,messages:[{messageId,authorAlias,text,sentAt,replyToId?}]}`; 최대 20건, 마스킹 |
| get_user_history | `{caseId,days?:30}`; 1~30 | `{effectiveViolationCount,cancelledCount,actions:[{actionId,caseId,type,status,expiresAt?}],recentMessageIds}` |
| get_stream_info | `{caseId}` | `{channelId,eventSummaries,officialDomains}` |
| get_channel_user_role | `{caseId}` | `{subjectAlias,role,isOfficialOperator}` |
| get_official_links | `{caseId}` | `{officialHosts,observedLinks:[{messageId,host,isOfficial}]}` |
| get_action_status | `{actionId}` | ActionResult; case 범위 서비스 권한 검사 |
| search_policy | `{query,category?:"HARASSMENT",policyVersion,topK?:4}`; query 1~1000자, topK 1~4 | `{matches:[{policyId,title,text,version,resourceUri,score}]}` |
| get_policy_section | `{policyId,policyVersion}` | `{policyId,title,text,version,resourceUri}`; Resource와 동일 원본 사용 |
| hide_message | ActionCommand, type=HIDE | ActionResult |
| timeout_user | ActionCommand, type=TIMEOUT, durationSeconds=300 | ActionResult |
| release_message | ActionCommand, type=RELEASE_HELD 또는 RESTORE_MESSAGE | ActionResult |
| revoke_timeout | ActionCommand, type=REVOKE_TIMEOUT | ActionResult |

Resource URI는 `policy://{version}/{documentId}/{sectionId}`로 고정한다. 인용한 원문·버전을 판단 시점에 스냅샷으로 보관한다. 임베딩 모델·차원·색인 버전을 기록하며 질의와 문서의 임베딩 설정을 일치시킨다.

ActionCommand의 필수 필드는 `caseId,actionId,planId,type,targetId,expectedCaseVersion,expectedTargetVersion,policyVersion,idempotencyKey`다. TIMEOUT에 `durationSeconds`, 취소 계열에 `originalActionId,decisionId`를 추가한다. 일반 자동 조치에는 decisionId가 없고 서버에 저장된 자동 계획으로 권한을 검증한다.

```json
{
  "caseId": "uuid",
  "actionId": "uuid",
  "planId": "uuid",
  "type": "TIMEOUT",
  "targetId": "channel-uuid:user-uuid",
  "expectedCaseVersion": 3,
  "expectedTargetVersion": 1,
  "policyVersion": "policy-v1",
  "idempotencyKey": "action:uuid",
  "durationSeconds": 300
}
```

ActionResult:

```json
{
  "actionId": "uuid",
  "caseId": "uuid",
  "type": "TIMEOUT",
  "status": "SUCCEEDED",
  "applied": true,
  "targetVersion": 2,
  "startedAt": "2026-10-19T03:00:00Z",
  "expiresAt": "2026-10-19T03:05:00Z",
  "replayed": false,
  "error": null
}
```

status는 `PENDING / RUNNING / SUCCEEDED / FAILED / UNKNOWN`이다. applied는 확인됨 true, 미반영 확인 false, 불명 null이다. 조치가 없는 404는 별도 오류이며 applied=false의 증거로 쓰지 않는다. 재시도 가능 오류는 `TEMPORARY_UNAVAILABLE`, 중단·재검토 오류는 `FORBIDDEN / POLICY_MISMATCH / STALE_VERSION / INVALID_EVIDENCE / IDEMPOTENCY_CONFLICT`로 구분한다. 도구 오류도 A.1 형식으로 반환하고 MCP 수준의 오류 여부를 함께 설정한다.

### A.6 State·상태 전이

| 필드 | 타입·초기값 | 갱신 주체 |
| --- | --- | --- |
| case_id, task_id, thread_id, trace_id | string, 서버 발급 | Backend·실행기 |
| channel_id, user_id | string, 사건에서 로드 | Backend |
| filter_result | REVIEW/HOLD/FLOOD | 초기 필터 |
| case_version, evidence_version | int | 사건 저장소 |
| dirty | bool=false | 사건 저장소 |
| message_ids, evidence_refs | string[]=[] | 사건 로드·검증 |
| tool_observations | object[]=[]; 원문 제외 | 조사 루프 |
| policy_version | string | 정책 로드 |
| policy_evidence | object[]=[] | 검색·원문 조회 |
| judgment | null 또는 VIOLATION/NO_VIOLATION/NEEDS_REVIEW | 모델 출력 검증 |
| requested_actions | object[]=[] | 모델 제안 |
| action_plan | null 또는 `{planId,actions:[ActionCommand]}` | Backend |
| idempotency_keys | actionId→key map | Backend 계획 |
| execution_results | ActionResult[]=[] | 실행·조회 |
| notification_status | PENDING/SENT/FAILED | 통지 작업 |
| appeal_id, decision_id | string 또는 null | 재검토 작업 |
| review_decision | null/UPHOLD/OVERTURN | 운영자 결정 저장소 |
| turn_count, retry_count | int=0 | 실행 예산 저장소 |
| checkpoint_ref, error | null 또는 object | 실행기 |

동시 조치가 있으므로 단일 idempotency_key 대신 action_plan의 조치별 키와 idempotency_keys 맵을 저장한다. 모델이 만든 키는 사용하지 않는다. 체크포인트 재시작도 turn_count와 retry_count를 0으로 초기화하지 않는다.

| 상태 대상 | 전이 |
| --- | --- |
| 사건 | COLLECTING → ANALYZING → NO_ACTION 또는 ACTIONED 또는 NEEDS_REVIEW |
| 사건 오류 | 조사/실행 실패·UNKNOWN → NEEDS_REVIEW; 실제 조치 상태는 별도 유지 |
| 실행 작업 | QUEUED → RUNNING → WAITING_REVIEW 또는 SUCCEEDED 또는 FAILED |
| 이의제기 | OPEN → REVIEW_PENDING → UPHELD 또는 OVERTURNED |
| 복구 작업 | 취소 결정 후 별도 ActionResult; OVERTURNED라도 복구 미완료 가능 |
| 메시지 | PUBLIC → HELD/HIDDEN; HELD → PUBLIC/HIDDEN; HIDDEN → PUBLIC은 유효 취소 결정 필요 |
| 제한 | 특정 actionId의 시작~종료 동안 유효; 만료·취소로 비활성 |

표의 ACTIONED는 해당 사건에서 확인된 조치가 있음을 뜻하며 모든 조치의 성공을 뜻하지 않는다. UI는 개별 ActionResult를 표시한다. 조사 작업 성공과 제재 성공, 취소 결정과 복구 성공을 합치지 않는다.
